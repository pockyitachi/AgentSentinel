# GUI Ledger 讲解版：拿“反复点保存”讲清楚

本篇用未开启 UI 树的截图版机制做概念讲解；当前 UI 树增强版的工作流、输入输出和边界条件见[技术详解](gui_ledger_implementation_zh.md)。真实运行输入输出的拆解属于本地未发布材料，不是阅读本文的前提。

## 1. 可以先直接这样介绍

> 我们在原来的 Qwen 手机操作助手旁边，加了一个记账和提醒的小程序，叫 GUI Ledger。
>
> Qwen 仍然负责看截图、理解任务和决定点哪里。Ledger 不再找另一个大模型评价它，而是记录实际执行的动作，以及动作前后的截图是否相同。
>
> 它有三个部分：第一部分记账；第二部分在 Qwen 每次思考前，把最近的执行情况整理成一张便条；第三部分检查 Qwen 准备做的动作是否又在重复。发现重复时，这次动作还是照常执行，只是执行后附上一条提醒，让 Qwen 下一轮能看到。
>
> 所以，它提供的是更明确的执行记录和重复提醒，不是代替 Qwen 判断任务完成了没有。

下面用同一个例子把这段话拆开。

## 2. 只看一个场景

用户的任务是：

> 把当前已经填好的备忘录保存下来。

手机停在编辑页面，右上角有“保存”按钮。假设 Qwen 连续点击同一个位置，每次执行器都正常返回，但取到的前后截图像素完全相同。

这是为了说明机制而构造的例子，不是某次真实评测记录，也不是说真实的保存操作一定会这样。

先区分两种“知道”：

- **Qwen** 可以从截图理解“右上角是保存按钮”。
- **Ledger** 不理解按钮含义。它只拿到“点击了哪个坐标”和“前后两张图片”。

我们给这张图片取个代号，叫“画面 A”。这个代号只是图片编号，不是 Ledger 识别出了“备忘录编辑页”。

## 3. 第一部分：记账——刚才到底发生了什么？

### 它拿到什么

以第一次点击为例，正常运行流程会把以下信息交给它：

```text
执行前：画面 A
实际动作：点击坐标 (500, 100)
执行结果：执行器正常返回
执行后：画面 A
```

这些来自实际执行过程，不是从 Qwen 写的“我已经保存成功”中提取的。

### 它怎么处理

它给图片和动作各做一个“指纹”，用来精确比较：

- 图片指纹：尺寸和像素相同，就视为同一个图片样本。
- 动作指纹：动作类型和参数相同，就视为同一个可比较动作。例如两次都点击 `(500, 100)`。

这是普通代码计算，不需要让模型看图，也不需要让模型读历史。账本保存的是指纹等记录，不是再存一遍完整图片或动作参数。

### 它产出什么

供后续程序使用的记录，用人话表达就是：

```text
第 1 步：执行了一次点击，执行器正常返回，前后采样都是 A。
第 2 步：执行了一次相同的点击，执行器正常返回，前后采样都是 A。
```

这两行是帮助理解的中文表达，不是实际存储格式。内部还保留动作指纹，后面的重复检查才知道两次点击不仅名字一样，参数也一样。

**它不能把这条记录写成“保存失败了两次”。** 页面没有变化，也可能是保存已经完成但页面不跳转，或者后台仍在处理。

讲给别人时，这个组件一句话就够了：

> 第一部分不负责判断对错，只负责把实际动作和前后截图的关系记下来。

## 4. 第二部分：Inform——Qwen 思考前，给它一张便条

### 它拿到什么

它拿到原任务、当前画面编号，以及刚才的账本。

现在前两次点击已经发生，Qwen 即将决定第三步。

### 它怎么处理

它用固定模板，把账本整理成一段文字，追加到这一次发给 Qwen 的请求中。不请模型总结，不请模型润色。

### 它产出什么

本轮便条的中文含义如下。程序实际使用英文模板，画面编号写作 `O1` 等；这里用 A 和中文方便讲解：

```text
你的任务：把当前已经填好的备忘录保存下来。
当前是第 3 步，当前采样画面编号为 A。
A 在第 1、2、3 步都出现过。

最近的执行记录：
- 第 1 步：点击，执行器正常返回，截图 A → A。
- 第 2 步：点击，执行器正常返回，截图 A → A。

注意：截图相同不代表整个环境没有变化；
截图变化也不等于任务进展；执行器返回不等于任务成功。
```

实际 Inform 的动作列表只展示“点击”等标签，**不展示坐标，也不写“你点击了保存按钮”**。判断两次点击参数是否相同是程序内部的工作。

原来的请求可以理解成：

```text
任务 + Qwen 原有步骤历史 + 当前截图
```

现在是：

```text
任务 + Qwen 原有步骤历史 + 当前截图 + 本轮执行便条
```

Qwen 看完后，仍然自己决定下一步。

### 这张便条会一直堆在历史里吗

不会。第三步用第三步的便条，第四步重新生成第四步的便条，不把旧便条一张张追加进 Qwen 历史。底层账本则继续更新。

讲给别人时可以说：

> 第二部分把“程序记录了什么”直接告诉 Qwen，让它在下一次决策时能用上这些信息。

## 5. 第三部分：Govern——Qwen 选好动作后，检查是不是又重复了

### 它拿到什么

假设 Qwen 看完第三步的请求，仍决定点击 `(500, 100)`。

这时 Govern 拿到三样东西：

```text
当前画面：A
此前记录：连续两次相同点击，正常返回，前后都是 A
本轮候选动作：再次点击 (500, 100)
```

### 它怎么处理

代码逐项比较：前两步是否连续？动作参数是否完全一样？是否正常返回？前后截图是否都与当前截图相同？

在这个例子中都满足，因此第三次点击命中重复规则。不需要模型回答“这样做合理吗”。

### 它产出什么

只有两种结果：

- **不提醒（ALLOW）**：不增加反馈，动作正常执行。
- **提醒（NUDGE）**：准备一条固定文本，动作仍然正常执行。

这里返回提醒，中文含义是：

> 这次动作与前面连续两次执行相同。那两次执行前后的截图，都与本次执行前的截图相同。这次动作仍然执行了。相同像素并不能证明后台没有变化或任务失败。

这条提醒**不是**“不要再点保存”，也不是“你保存失败了”。当前程序没有下这样的结论。

### 最重要的时间点

**第三次点击不会被取消，也不会让 Qwen 当场重选。**

程序先执行第三次点击。正常返回并完成记录后，把提醒留给下一轮；Qwen 在第四轮请求里才收到它。

而且，触发提醒依据的是第三次点击前已有的记录：第三次点击之后即使画面变了，仍可能发送这条描述此前重复情况的提醒，不能把它解读成“三次都失败了”。

讲给别人时可以说：

> 第三部分不替 Qwen 操作，只在检测到重复时，把这件事作为执行反馈告诉下一轮的 Qwen。

## 6. 四轮连起来，就没有神秘的地方了

| 哪一轮 | 决策前告诉 Qwen 什么 | Qwen 选好动作后，程序做什么 |
| --- | --- | --- |
| 第 1 轮 | 当前是 A，还没有已执行动作 | 执行点击，记下 A → A |
| 第 2 轮 | 上次点击正常返回，截图 A → A | 再执行点击，再记一条 |
| 第 3 轮 | 前两次点击正常返回，截图都为 A → A | 发现本次又是相同点击；仍执行，之后暂存提醒 |
| 第 4 轮 | 更新后的便条，加上上一轮执行后暂存的重复提醒 | Qwen 自己决定继续点击、等待、返回，还是做别的 |

第四轮收到的提醒，会附在第三轮原有步骤描述后面，作为执行反馈保留在历史里。它和“每轮重新生成、不会堆进历史的 Inform 便条”不同。

这就是三个部分的分工：

> **账本保存记录；Inform 把记录讲给模型听；Govern 针对新动作提供重复提醒。**

## 7. 除了重复点击，还检查什么？

当前还检查一种短循环，例如：

```text
画面 A → 执行动作 a → 画面 B
画面 B → 执行动作 b → 画面 A
画面 A → 执行动作 a → 画面 B
画面 B → 执行动作 b → 画面 A

接下来又准备执行 a：产生重复序列提醒。
```

同样要求实际动作参数和相连的采样画面对应得上，不是看到“点一下、返回、点一下、返回”的文字就判断出循环。

为了不每轮都重复提醒，默认一次任务尝试最多提醒 5 次；一次提醒后至少间隔 3 次已登记执行，再考虑下一次提醒。提醒与否都不拦截原动作。

目前主要就是这两类规则，不是一个能评价任意操作是否合理的通用裁判。

## 8. 别人追问时，最容易讲清楚的几个回答

**“不调用额外模型，怎么知道 agent 卡住了？”**

严格说，它不知道 agent 一定卡住了。它只检测到精确的重复模式。判断这些重复有没有问题、下一步怎么做，仍交给 Qwen。

**“截图是谁看的？”**

Qwen 负责理解截图内容。Ledger 只用程序比较图片像素，没有第二次视觉模型调用，也不识别截图上的文字。

**“那 agent 说‘我保存成功了’，你们能纠正吗？”**

当前不能直接判定这句话真假。Ledger 可以给出执行记录，但没有语义真假判断器，也不会删除那句话。

**“是不是已经知道任务完成到哪一步了？”**

不是。它知道执行了几步、有哪些采样画面和重复操作，不知道“已完成填写、还差提交”这种业务进度。

**“为什么模型自己有历史，还需要这个？”**

模型的原生历史包含它对操作的描述和结论。这里额外提供的是程序从实际执行和截图比较中整理出的记录，例如“调用返回了，但前后采样像素相同”。希望它能帮助决策，但是否真的提高成功率，要看对照实验。

**“打开 INFORM 和 FULL 有什么区别？”**

INFORM 只给每轮便条；FULL 在便条之外，再加上执行后的重复提醒。OFF 两者都不加。

**“没有额外模型调用，是不是更省 token？”**

不一定。便条和提醒本身会增加输入 token；它们需要带来其他消耗的减少，例如减少后续尝试或缩短输出，总消耗才可能下降，需要实测。

## 9. 最后怎么收尾

> 我们目前做的不是一个更强的模型裁判，而是给现有 Qwen 补了一套程序化的执行记录和反馈。程序能精确检查的部分交给程序：动作是否重复、截图样本是否相同。任务含义和下一步决策，还是交给原来的 Qwen。
>
> 这样可以测试：在不增加另一个模型来做判断的情况下，仅靠这些记录和提醒，能不能让 GUI agent 做得更好。

这就是当前实现的目标，不代表效果已经被证明。
