## 范围与判定口径

- 数据范围严格限定为 `/Users/apigo/Desktop/Projects/QR-MW/traj_logs/seed_baseline`；没有读取或混入 `pilot_baseline`、`qverifier` 或其他 run。
- 证据来自同一 task 目录下的 `traj.json`、原始 `screenshots/`、`thread_*.log` 与 `result.txt`。
- 时序统一为 `S_t → P_t → A_t → S_{t+1}`：`S_t` 是第 t 次模型调用看到、且在执行 `A_t` 之前保存的截图。因此，不能用 `S_t` 去证明 `A_t` 已执行；`A_t` 的结果要看 `S_{t+1}`。
- `CONFIRMED` 表示：source 中有可反驳的事实性 claim；后续 target 明确引用/复述它；并沿该 premise 采取动作或改变方向。它不声称已经做了“删掉 history 后结果一定改变”的反事实因果实验。
- `CANDIDATE` 表示复用只是语义近似、值又发生突变，或没有完成外部动作；`SELF-CORRECTED` 表示错误 history 确实影响了下一步，但在错误写入/发送之前被当前 GUI 修正。
- 证据层级：`GUI 直证` 是屏幕上的文件、消息、日历、地图或链接预览直接反驳 claim；`Evaluator 依赖` 表示精确的最终任务正确性、集合穷尽性或 backend 状态还需 evaluator/result 佐证。没有把“只有 score=0、没有直接反证”的案例标成 `CONFIRMED`。

## 对 Sentinel 设计最关键的分层结论

在 17 个 `CONFIRMED` 中：

- 11 例的 source action 已把错误 claim 写入/选择进当前 GUI（SBP-001/002/004/006/007/009/010/011/013/015/016）。target 同时看到错误 history 与错误 GUI state。此时只删 pre-step 文本未必够；Sentinel 更理想的拦截点是执行 `A_s` 之前，或需要附带 state repair / rollback。
- 1 例（SBP-003）是错误 history 与既存坏表单默认值互相强化；虽然 source action 只写标题，target 仍同时获得 history 和 GUI 的错误执行状态。
- 1 例（SBP-005）更强：当前 GUI 已直接反驳 history，target 仍听从 history。这是 state-aware consistency check 最适合捕获的类型。
- 4 例是首个 target 的 claim-bearing evidence 几乎只来自 history（SBP-008/012/014/017）。这些是最干净的“判定 pre-step 无效后不注入 prompt”MVP 样本；其中 SBP-012 与 SBP-017 是 exact decision-state propagation，SBP-008 是语义漂移，SBP-014 是分类 premise 延续。
- 两个 `SELF-CORRECTED`（SBP-018/019）说明不应把检测到矛盾一律等同于 task failure：当当前 GUI 的直证足够强时，agent 可以覆盖坏 history。Sentinel output 应允许 `DROP/DEPRIORITIZE + trust current observation`，而不是必然 abort。
- 唯一 `CANDIDATE`（SBP-020）保留为边界样本：方向继承了，但精确数值突变且没有发送，所以不升级为 confirmed。

机器可读明细在 `propagation_cases.jsonl`；每行已加入 `evidence_basis`、`source_action_gui_effect`、`target_context_mode`、`thread_request_verified`，9 个已核验例另含 `thread_log_ref`。
